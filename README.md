# ВышКат

Консольное приложение для учёта парка транспорта и вещей. Go 1.22+, внешние библиотеки не нужны.

## Запуск

Из корня проекта:

```bash
go run ./cmd/vyshkat
```

Тесты и покрытие:

```bash
go test ./... -v
go test ./... -cover
```

## Структура

- `cmd/vyshkat/main.go` — только создание зависимостей и запуск демонстрации.
- `internal/park/transport.go` — интерфейсы транспорта и энергопотребления.
- `internal/park/item.go` — интерфейс инвентаризируемых объектов.
- `internal/park/scooter.go`, `bicycle.go`, `electric_bicycle.go` — модели транспорта и конструкторы.
- `internal/park/helmet.go`, `charging_station.go` — модели вещей и конструкторы.
- `internal/park/service.go` — интерфейс техосмотра и простая реализация.
- `internal/park/park.go` — учёт, проверка при добавлении, отчёты.
- `internal/park/container.go` — простой контейнер зависимостей.
- `internal/park/demo.go` — демонстрация сценариев и вывод в консоль.
- `internal/park/park_test.go` — тесты поведения.

Поля моделей не экспортируются, создание объектов происходит через `NewScooter`, `NewBicycle` и другие конструкторы. Это не даёт вызывающему коду напрямую изменять поля. Для примера, `NewScooter("Ninebot", 101, 0.5, 8)` создаёт самокат.

## Возможности

- Приём техники после техосмотра и отклонение некорректной техники.
- Проверка уникальности инвентарного номера среди транспорта и вещей.
- Подсчёт количества транспорта и вещей, суммарного суточного потребления энергии.
- Список транспорта для новичков: простота не меньше 6.
- Полный список инвентаря.
- Демонстрация успешного и неуспешного добавления, отказа техосмотра, дубликата и отчётов.

## SOLID

- **SRP:** `Park` хранит объекты и формирует отчёты, `RegularService` проводит техосмотр, `RunDemo` отвечает за консольный вывод.
- **OCP:** `Park` использует интерфейс `Transport`. Чтобы добавить новый транспорт, достаточно создать тип с методами `GetName`, `GetNumber`, `GetEase` (и `GetEnergy` для электрического устройства). Код `Park` менять не нужно.
- **LSP:** самокат, велосипед и электровелосипед взаимозаменяемы в методе `AddTransport`, так как реализуют `Transport`.
- **ISP:** энергопотребление выделено в отдельный интерфейс `EnergyConsumer`. Обычный велосипед не обязан иметь `GetEnergy`.
- **DIP:** `Park` зависит от интерфейса `ServiceCenter`, а не от конкретного `RegularService`. Контейнер `NewContainer` связывает зависимости при запуске.

Сознательное упрощение: весь домен находится в одном пакете `park`, без отдельных слоёв репозиториев, фабрик и базы данных. Для небольшого консольного приложения это снижает сложность.

## Как расширять

Новый вид транспорта: добавить отдельный файл и конструктор, реализовать `Transport`. Для демонстрации нового вида также добавить создание объекта в `RunDemo`. Методы `Park` останутся прежними.

Сотрудники: создать отдельную модель и механизм учёта сотрудников, не добавляя их в `Inventory`, потому что сотрудники не ставятся на баланс. Склад: создать отдельный модуль для учёта запчастей; при необходимости связать его с парком через интерфейс.

## Тестирование и подмена техосмотра

`TestInspection` передаёт в `NewContainer` объект `FakeService` вместо `RegularService`. При `allow: false` транспорт отклоняется, при `allow: true` принимается. `TestBeginners` проверяет порог 6. `TestEnergy` проверяет сумму для электрического и обычного транспорта и зарядной станции. Остальные тесты проверяют номера, ошибочные входные данные и конструкторы.
